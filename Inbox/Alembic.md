Good frame — most of the concepts map over, but a few key differences trip people up coming from Django.

## Quick mapping

|Django|Alembic|Notes|
|---|---|---|
|`makemigrations`|`alembic revision --autogenerate -m "..."`|Same idea: diff models vs. last known state|
|`migrate`|`alembic upgrade head`|Apply pending migrations|
|`migrate app 0003`|`alembic upgrade <revision>`|Go to a specific point|
|`migrate app zero`|`alembic downgrade base`|Roll back everything|
|`showmigrations`|`alembic history` + `alembic current`|Split into two commands instead of one|
|`django_migrations` table|`alembic_version` table|Tracks applied state — but see below, this is a big difference|

## The important structural differences

**1. Linear chain vs. per-app tracking.** Django tracks applied migrations _per app_, as a list — each app has its own sequence, and Django resolves cross-app dependencies via the `dependencies` list in each migration file. Alembic has **one global chain** per `alembic_version` table (you can configure multiple bases for multiple DBs, but by default it's one linear/branching history for everything). This is why `alembic heads` matters — Django doesn't really have an equivalent because each app's head is tracked separately.

**2. `alembic_version` only stores a single revision ID**, not a full history log. Django's `django_migrations` table logs every migration ever applied with timestamps. Alembic just knows "the DB is currently at revision X" — to see history you read the _migration files themselves_ (`alembic history`), not the DB.

**3. No built-in dependency graph across "apps."** Django auto-resolves migration order across apps based on model relationships and explicit `dependencies`. Alembic doesn't know about "apps" at all — it's just Python/SQLAlchemy metadata. If you have multiple models modules, you're responsible for making sure `env.py` imports all of them so autogenerate sees the full picture.

**4. Merge conflicts feel different.** Django's `makemigrations --merge` handles conflicting migrations within an app. Alembic's `alembic merge heads` does the same thing but conceptually it's merging two branches of _one_ chain, since everything lives in a single revision tree.

**5. `upgrade()`/`downgrade()` are plain Python + SQLAlchemy Core `op.*` calls**, not Django's more abstract `operations = [...]` list. More power (can drop into raw SQL trivially via `op.execute`), less declarative safety — Alembic won't stop you from writing a downgrade that doesn't actually reverse the upgrade correctly.

**6. No `--fake` equivalent by default**, but same idea exists: `alembic stamp <revision>` marks the DB as being at a revision without running the migration — used the same way you'd use `migrate --fake` (e.g., syncing state after manually applying SQL, or bootstrapping an existing DB).

## Workflow-wise, the loop is nearly identical

```
Django:  edit models → makemigrations → review file → migrate → test → commit
Alembic: edit models → alembic revision --autogenerate → review file → alembic upgrade head → test → commit
```

The main adjustment from Django habits: **review autogenerated files more skeptically** — Alembic's diffing is less mature than Django's (it can miss column renames, some constraint changes), and there's no `sqlmigrate`-style dry-run command built in — closest equivalent is `alembic upgrade head --sql` which prints the SQL without executing it.
